# M3: identities

The working plan for milestone M3 in [PLAN.md](../../PLAN.md).
[SPEC.md](../../SPEC.md) (draft-02) is the source of truth. If this file
and the spec disagree, the spec wins: report it rather than work around
it. [M2-M5.md](M2-M5.md)'s "Conventions" and "How the work is split"
still apply.

## Goal

At the end of M3, people sign in as identities and use rooms as
themselves, from several devices:

- AUTH with ML-DSA-44 key files fetched over HTTPS, under the rules of
  4.4 and 4.5. Hosted identities use the server's own records.
- REGISTER under the server's identity domain. Hosted key files are
  written to a directory and, optionally, served by `risalad`'s own
  HTTPS listener at `/.well-known/risala/<name>` (PLAN.md section 6).
- KEY LIST, ADD and DEL, and UNREGISTER.
- Identities stay members across connections. Every device gets live
  events from the moment it signs in, with no JOIN. Identities may create
  rooms by joining them, and the creator is the owner.
- READ markers, TYPING, NAME, MEMBERS, WHOIS and PRESENCE.
- BLOCK, UNBLOCK and BLOCKS. They are stored now, and take effect on
  direct conversations in M5a.
- cids for identities, kept for 24 hours across connections.
- librisala and `risala-cli` sign in as identities, register, manage
  keys, and expose read markers, typing, names, members and presence.

**Direct conversations move to M5a.** In draft-02 they start with INIT
and are always encrypted (5.1, 12.3), so they cannot exist without MLS.

**Not in M3:** ADMIN commands, roles beyond the creator's ownership,
SET, INVITE, KICK and BAN (M4). Encryption (M5a). Push and uploads (M8).

## Carried in from M2

`M2-M5.md`, "Carried into M3", lists hub design work M3 must do first:

- Rooms created at run time, with a lock so two JOINs do not both create
  one.
- A "dropped" flag on room entries.
- Membership keyed by conversation id.
- A conversation abstraction that will also fit direct conversations.
- Less work under the global registry lock during fan-out.

## Wave 1 (in parallel)

### A. Server core for identities (`crates/risala-server/src/core/`, `src/store/`)

- **The hub carry-overs above.**
- **AUTH (4.5):**
  - Build the challenge with this connection's SNI host and nonce, and
    use up the nonce whether AUTH succeeds or not.
  - Use the hosted identity's own keys, or else a key file from the
    `KeyFetcher` trait. Task B implements it; use a stub in tests.
  - Refetch once when a cached file fails to verify. Never block the
    room locks on a fetch.
  - Reply `op=yes` for operators from `config.operators`.
  - Record the device key on the connection.
- **REGISTER (4.6):** under `identity_domain`, with `registration`
  open or closed (10.6), and a simple per-address rate limit (13). A
  name that was ever unregistered can't be registered again (4.8,
  10.5). The connection is signed in at once. Publishing the key file
  goes through a `KeyFilePublisher` trait, which task B implements.
- **KEY LIST, ADD and DEL (4.7)** for hosted identities. Refuse to
  delete the last key. Close the connections signed in with a removed
  key, and republish the key file.
- **UNREGISTER (4.8).** If `purge=yes` needs DELETE (M4), reply
  `not-supported` for it and leave a note.
- **Identity membership:**
  - Membership persists across connections, and fan-out reaches every
    device.
  - Identities may create rooms by joining them, depending on a config
    policy, and the creator becomes the owner.
  - SYNC reports read markers.
  - A device signed in with a key that was later removed from the
    identity's key file is closed (4.4) when the server notices.
- **cids:** 24 hours for identities, across connections and per
  conversation id (7.6).
- **Config:** `identity_domain`, the room creation policy, and the
  registration rate limit. Task B owns the `[http]` and `[keys]` config
  sections. You own the rest.

### B. HTTPS: key file fetching and hosting (new crate `crates/risala-keyfetch`, `crates/risala-server/src/http/`)

- **`risala-keyfetch`**, shared by the server (for AUTH) and later by
  librisala (12.12):
  - an HTTPS GET client using rustls with aws-lc-rs, with roots that can
    be configured (public roots by default, test roots in tests)
  - TLS 1.3 required and TLS 1.2 refused, unless the spec says otherwise
  - no redirects, and only a 200 response counts
  - 10 seconds and 256 KiB at most
  - parsing with `risala_proto::keyfile`
  - a cache of up to one hour, with an explicit "refetch" for the
    once-on-failure rule
  - an optional guard that refuses special-purpose addresses (RFC 6890)
    after DNS resolution, including on every redirect-free connect and
    every address tried. Servers must turn it on (4.4), and operators
    may allow private addresses in config.
  - It implements the server's `KeyFetcher` trait, through a thin
    adapter in the server crate. Agree on the trait with task A's
    description: `async fn fetch(&self, identity, refresh: bool) ->
    Result<Vec<PublicKey>>`. If the trait needs something else,
    implement what A needs and report it.
- **`risalad`'s HTTPS listener:** optional, set in `[http]`, with its
  own certificates by SNI (reuse `net::tls`). It serves
  `/.well-known/risala/<name>` from the hosted identities' keys, with
  `Content-Type: text/plain; charset=utf-8`. Anything else gets 404.
- **Key file directory writer:** implements `KeyFilePublisher`, writing
  `<dir>/<name>` atomically and deleting it on UNREGISTER, so operators
  can serve the directory from their own web server instead.
- **Tests:**
  - a local HTTPS server with a test CA
  - redirects refused, size and time limits, and non-200 responses
  - the address guard, against 127.0.0.1, ::1, 10/8, 169.254/16 and
    fc00::/7, using DNS names that resolve to them through an injected
    resolver
  - the cache and refetch
  - the listener serving a hosted identity's key file, end to end

### C. librisala and CLI for identities (`crates/librisala/src/conn/`, `src/client/`, `crates/risala-cli`)

- **Identity accounts end to end:**
  - device key generation and storage through `KeyStore`
  - AUTH, plus REGISTER (with INFO for the identity domain first)
  - the key file line to publish for self-hosted identities
  - KEY LIST, ADD and DEL
  - UNREGISTER, which also deletes the account's cache

  Errors are typed: `auth-failed`, `name-taken`, `forbidden`, and no
  registration on this server.
- **CLI:**
  - `register <server> <name>`
  - `login <server> <identity>`, using an existing key
  - `keys list`, `keys add` (shows a new device's key line) and
    `keys del`
  - `unregister`
  - `keygen` and `keyline` already exist
- **Tests** use a scripted server until A and B land, then `TestServer`
  in wave 2.

## Wave 2

### D. Server: the rest of M3 (`core/`)

- **READ (7.4):** sent to the account's other connections.
- **TYPING (8.1):** not sent to blocked people.
- **NAME (8.2):** persisted for identities, kept for the session for
  guests.
- **MEMBERS and WHOIS (8.3).**
- **PRESENCE (8.3):** batched, with the 30-second offline delay, sent
  only to people who share a conversation, and split to fit the line
  limit.
- **BLOCK, UNBLOCK and BLOCKS (5.7):** stored and listed now. Their
  effect on direct conversations comes in M5a.
- **End-to-end tests over TLS** for everything in M3, with `TestServer`
  extended to host identities and serve key files from a test HTTPS
  server.

### E. librisala: the rest of M3

- **Read markers:** sent, received from other devices, and reflected in
  unread counts.
- **Typing, names, members and presence:** each as an API for the apps.
- **BLOCK:** an API, and hiding blocked people in rooms on the client
  side (5.7).
- **Integration tests** against `TestServer` with two devices of one
  identity: live events reach both, and read markers sync between
  them.
