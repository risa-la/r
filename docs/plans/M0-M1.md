# M0 and M1: scaffold and `risala-proto`

This is the working plan for the first two milestones in
[PLAN.md](../../PLAN.md). [SPEC.md](../../SPEC.md) is the source of truth.
If this file and the spec disagree, the spec wins.

## Goal

At the end of this work:

- The Cargo workspace builds, with `risala-proto`, `risala-server`
  (`risalad`) and `librisala` under `crates/`.
- `nix flake check` runs fmt, clippy and the tests, and CI runs it.
- `risala-proto` parses and serialises every line in the spec, typed in
  both directions, and passes the Appendix B vectors.
- Property tests and a fuzz target exist and run clean.

The server and librisala stay empty skeletons. They start in M2 and M5.

## How the work is split

Each task runs in its own git worktree, branched from the scaffold
commit, and commits there. The parent merges the branches.

- **Own your files.** Edit only the files your task lists. Do not edit
  `src/lib.rs`, `src/error.rs` or another task's module. If you need a
  change there, say so in your report.
- **Dependencies.** The crate already depends on `base64`,
  `ed25519-dalek` (with `pem`), `sha2` and `thiserror`, with `proptest`
  for tests. Add a dependency only if you have to, and say why.
- **Errors.** Every parse function returns
  `Result<_, risala_proto::error::ParseError>`. Use `BadSyntax("...")` for
  grammar errors, `TooLong` for length limits and `UnknownVerb` for unknown
  verbs.
- **Done means:** `cargo fmt --all --check`,
  `cargo clippy --workspace --all-targets -- -D warnings` and
  `cargo test --workspace` all pass. Every public item has a doc comment
  that names the spec section it implements.
- **Commits:** plain messages in the imperative, for example
  "proto: parse lines and tags". No Co-Authored-By lines and no mention of
  AI tools.

## Conventions across the crate

- **Newtypes that check themselves.** A `Room` value is always a valid
  room. Types implement `FromStr` (which validates and folds case),
  `Display` (the wire form), `as_str()` where the wire form is a string,
  `Clone`, `Debug`, `PartialEq`, `Eq`, `Hash`, and `Ord` where it makes
  sense.
- **Case folding (3.5).** Names, verbs, option keys and fixed keywords
  such as `yes`, `owner` or `server` are case-insensitive. Parsing folds
  ASCII upper case to lower case. Serialising always writes lower case,
  and writes verbs in upper case.
- **Text stays escaped.** Text parameters are kept exactly as on the
  wire (3.4). Servers relay text unchanged, and length limits apply to
  the escaped form. Only `text::unescape` produces display text.
- **Be lenient where the spec says so.** Unknown tags are ignored (3.2).
  Unknown error codes, presence values and settings keys are kept, not
  rejected. Unknown options on a command are `BadSyntax` (3.3).

## Wave 1

### A. Lines (`frame.rs`, `line.rs`, `tests/common`, `tests/spec_lines.rs`)

`frame.rs` (2.3):

- `MAX_CLIENT_LINE = 8192` and `MAX_SERVER_LINE = 16384`, in bytes,
  including the LF.
- `LineDecoder`: a sans-I/O decoder. `LineDecoder::new(max_len)`,
  `push(&[u8])` and `next_line() -> Option<Result<String, ParseError>>`.
  - It strips the LF and one CR before it.
  - It checks UTF-8 and control characters.
  - A line that is too long is discarded up to the next LF and reported
    once as `TooLong`.
  - Memory stays bounded by `max_len` even while a long line is being
    discarded.
  - It yields empty lines as `Ok("")`. The caller ignores them, but they
    still reset idle timers (11).
- `check_line(&str)`: the same character checks for outgoing lines.

`line.rs` (3.1-3.3):

- `Tags`: ordered, with unique keys, each with an optional value. It
  provides `get(key) -> Option<&str>` (the value), `has(key)`,
  `insert(key, Option<value>) -> Result<..>` (checks the grammar and
  replaces an existing key), `remove`, `iter` and `is_empty`. Parsing
  rejects repeated keys and bad keys or values.
- `Line { tags, verb, params }`. `Line::parse(&str)` takes a line without
  its LF. The verb is kept as written. `params` is the raw rest of the line
  after the single space that follows the verb. `Display` writes the line
  back. For any line in canonical form (single spaces), parsing and then
  displaying gives back exactly the same string.
- `Params`: a cursor over `params` with `token()`, `options()` (the
  remaining `key=value` tokens, keys folded, duplicates rejected), `text()`
  (everything after exactly one space following the last token read) and
  `end()` (fails if anything is left). Accept runs of spaces between
  tokens. Text keeps any further leading spaces.
- `LineBuilder` for serialising: `Line::builder("MSG")`, `.tag(k, v)`,
  `.flag(k)`, `.token(t)`, `.option(k, v)`, `.text(t)` and `.build()`.
  Empty text leaves out the trailing space (see 5.4's `deleted` example).
- `tests/common/mod.rs` provides
  `spec_examples() -> Vec<Example { dir: Dir, line: String, spec_line: usize }>`.
  It collects every `C:` and `S:` line inside code blocks in SPEC.md, plus
  the session in README.md and the AUTH command in Appendix B. It skips
  prose such as "(the client PUTs ...)".
- `tests/spec_lines.rs` checks that every example parses as a `Line` and
  displays back unchanged.

### B. Values (`names.rs`, `time.rs`, `text.rs`, `types.rs`)

`names.rs` (3.5, 5.7, 10.2):

- `Name` (1-32 characters), `Domain` (A-labels, at least two labels,
  labels 1-63 characters with no hyphen at either end, 253 characters at
  most), `Uid` (guest `~name` or identity `name@domain`, with `is_guest()`,
  `name()` and `domain()`), `Room` (with the `#`, plus `bare()` without
  it, for URIs), `Conv` (a room or a uid), `Seq` (1 to 2^63-1, no leading
  zeros) and `Id` (1-64 characters of `a-z 0-9 - _`).
- `BlockTarget`: an identity, or `*@domain` (5.7).
- `ServerBanTarget`: an identity, `*@domain`, a guest, an IP address or
  a CIDR prefix (10.2).

`time.rs`: `Timestamp`, milliseconds since the Unix epoch. It parses and
formats exactly `YYYY-MM-DDTHH:MM:SS.mmmZ` and rejects invalid dates. It
offers `from_unix_millis`, `unix_millis` and `now()`. Write the calendar
code by hand; no new dependency.

`text.rs`:

- `escape(&str) -> String` for user input. A line break becomes `\n` and
  a backslash becomes `\\`. Decide what to do with other control
  characters and document it.
- `unescape(&str) -> Cow<str>` (3.4).
- `mentions(escaped: &str) -> Vec<Uid>` (5.5): the `@` comes at the start
  or after whitespace, once unescaped. The mention is the longest uid,
  without a trailing `.`. Names are folded and duplicates removed.

`types.rs`:

- `Role` (owner, mod, member) and `InfoRole`. INFO's role adds `none`, so
  use `Option<Role>` or a separate enum.
- `Presence` (online, offline, `Other(String)`) and `GuestAccess` (none,
  read, write).
- `RoomRetention` (`server` or a number of days, at least 1) and
  `ServerRetention` (`forever` or days).
- `Relation` (`Reply`, `Edit` or `React` with a `Seq`, 5.3).
- `Ref` and `Cid`: tag-value tokens of at most 64 bytes.
- `RoomSetting` (6.2): topic, public, guests, retention, or
  `Other { key, value }`.
- `ServerSetting` (10.6): guests, registration, retention, welcome, or
  `Other`.
- `PushReason` (dm, mention, reply, read, 9.3).
- Constants for the protocol's limits: a tag token is at most 64 bytes, a
  reaction 64, a topic 512, a report reason 512, a display name 128 and a
  file URL 512.

### C. Keys (`auth.rs`, `keyfile.rs`, `fingerprint.rs`)

`auth.rs` (4.5, Appendix B):

- `CHALLENGE_PREFIX`.
- `Nonce`: lower-case hex, at least 16 bytes, with `from_bytes`. Nonce
  generation is left to the caller, so the crate needs no RNG.
- `challenge_bytes(host, &Nonce, uid: &str) -> Vec<u8>`. It lower-cases
  the host and the uid.
- `PublicKey`: 32 bytes, base64 with padding, 44 characters, decoded
  strictly.
- `Signature`: 64 bytes, base64, 88 characters.
- `SecretKey`: `from_seed([u8; 32])`, `from_pkcs8_pem`, `to_pkcs8_pem`,
  `public_key()` and `sign_challenge(host, nonce, uid)`.
- `PublicKey::verify_challenge(host, nonce, uid, &Signature) -> bool`,
  using strict verification.
- Tests: every value in Appendix B, byte for byte, including the 82-byte
  challenge and the PEM.

`keyfile.rs` (4.4):

- `KeyFile::parse(&str)` keeps `KeyEntry { key: PublicKey, label: Option<String> }`.
  - It ignores blank lines, `#` lines, other key types and malformed
    lines, and keeps at most `MAX_KEYS = 64`.
  - It accepts CRLF.
- `MAX_KEY_FILE_BYTES = 65536`.
- `KeyEntry` displays as its key file line.
- `well_known_url(name, domain)` returns
  `https://<domain>/.well-known/risala/<name>`.

`fingerprint.rs` (2.2): `Fingerprint`, the SHA-256 of a DER-encoded
SubjectPublicKeyInfo. It has `from_spki_der`, displays as
`sha256:<64 lower-case hex>`, and parses that form back.

## Wave 2

### D. Commands (`command.rs`, `tests/spec_client.rs`)

- `Request { ref_: Option<Ref>, command: Command }`.
- `Request::parse(&Line) -> Result<Request, ParseError>` and
  `Request::to_line(&self) -> Line`.
- `Command` has one variant per command in Section 12, using the types
  from wave 1.
  - MSG carries its `Relation`, `file` and `cid` tags.
  - Subcommands (KEY, PUSH, ADMIN) are nested enums.
- Arity, option and tag rules follow 3.3 and 5.3:
  - The wrong number of tokens, or an unknown option, is `BadSyntax`.
  - More than one relation, or `file` with `edit` or `react`, is
    `BadSyntax`.
  - Values over a protocol limit are `TooLong`.
  - An empty MSG text is `BadSyntax`.
- `tests/spec_client.rs`: every `C:` example parses. Serialising gives
  back the same line with the verb in upper case.

### E. Server lines (`server.rs`, `tests/spec_server.rs`)

- `ServerMessage::parse(&Line) -> Result<ServerMessage, ParseError>` and
  `ServerMessage::to_line(&self) -> Line`.
- It covers every line in the second table of Section 12:
  - the greeting, OK with its result values, and ERR with its code
  - events, with `seq`, `t`, `from`, the relation, `file`, `file-type`,
    `file-size` and `deleted`
  - snapshots, which are events without that metadata
  - every response line, and reports with their `report` tag
  - PRESENCE, READ, TYPING, NAME, NOTICE, DROP, PING and BYE
- `ref` is kept on every line.
- An unknown verb parses as `Unknown(Line)`, not an error (3.8).
- Also covered: the NOTIFY push body (9.3).
- `tests/spec_server.rs`: every `S:` example parses and serialises back
  unchanged.

### F. Property tests and fuzzing (`tests/props.rs`, `fuzz/`)

- Property tests:
  - Parsing what we serialise gives back the same value, for `Line`,
    `Tags`, names, `Timestamp`, escaping and key file lines.
  - `LineDecoder` never panics, never exceeds its memory bound and agrees
    with a simple reference splitter.
- `crates/risala-proto/fuzz` (its own workspace, excluded from the main
  one) has these targets:
  - `frame` (bytes into `LineDecoder`, then `Line::parse`)
  - `client` (then `Request::parse`)
  - `server` (then `ServerMessage::parse`)
  - `keyfile`
- Every target that parses successfully serialises and parses again, and
  checks it gets the same value.
- Run each target for a short time if a toolchain is available.
  `RUSTC_BOOTSTRAP=1` lets the stable toolchain run cargo-fuzz.

## Wave 3: review

A reviewer reads the whole crate against the spec and lists problems:

- places where the code disagrees with the spec
- places where the spec is ambiguous
- missing cases
- API problems that would hurt the server or librisala

The parent fixes them, then reruns the full checks and `nix flake check`.

## Not in this work

- The spec gaps still open in PLAN.md section 5, item 7. These need
  decisions from the spec's authors.
- Anything with sockets, TLS or storage. That starts in M2.
