# M4: rich messages and moderation

The working plan for milestone M4 in [PLAN.md](../../PLAN.md).
[SPEC.md](../../SPEC.md) (draft-02) is the source of truth. If this file
and the spec disagree, the spec wins: report it rather than work around
it. [M2-M5.md](M2-M5.md)'s "Conventions" and "How the work is split"
still apply, with the changes below.

## Goal

At the end of M4, rooms can be run and kept clean:

- Replies, edits and reactions (5.3), DELETE (5.4) and RELATED (7.3).
- Room settings with SET (6.2), roles with ROLE and ROLES (6.3), and
  INVITE, KICK, BAN, UNBAN and BANS (6.4).
- REPORT, REPORTS and RESOLVE (5.8), delivered live to reviewers.
- Retention (7.5), for the server and per room.
- Every ADMIN command (Section 10).
- UNREGISTER `purge=yes` (4.8).
- librisala and `risala-cli` expose all of it.

**Not in M4:** direct conversations, REPORTENC and everything else in
Section 12 (M5a). In M4, every room has `e2ee=no`, so the rules for
encrypted rooms never apply, but checks that cost nothing (for example
`SET <room> e2ee` gets `forbidden`) are written now. Files and push
(M8).

## Decided before starting

Confirmed with the user on 2026-11-08 (PLAN.md section 5, item 30):

- Authors may DELETE their own messages in a room they can no longer
  read (5.4).
- KICK of a non-member gets `not-found`, even if they hold a role (6.4).
- Room BAN of a guest bans the uid only. ADMIN BAN of a connected guest
  bans its IPv4 address or its IPv6 `/64` (10.2).
- `ADMIN SET guests no` ends the sessions of connected guests (10.6).
- ADMIN DROP of a room from the configuration creates it again at once,
  empty and with a new id (PLAN.md section 6).

## Scaffold (done)

On branch `m4`:

- `Store` has four supertraits, one per area: `MessageStore`,
  `ModerationStore`, `ReportStore` and `AdminStore`, each in
  `store/<area>.rs`, with its SQLite implementation in
  `store/sqlite/<area>.rs`. Add your store methods to your trait only.
  The `Flaky` test store in `core/tests.rs` has one empty block per
  trait; add your delegations to your block only.
- `core/commands.rs` routes M4's commands to one method per area, in
  `core/messages.rs`, `core/moderation.rs`, `core/reports.rs` and
  `core/admin.rs`. Each now replies `not-supported`.
- The test `later_commands_are_not_supported` now lists only files.

## How the work is split

As in M2-M5.md, with these changes:

- **Branches are rebased, never merged.** The parent rebases each task's
  branch onto `m4` and fast-forwards. Keep your commits small and
  self-contained so the rebase is easy.
- **Schema changes:** if you need one, add a migration at the end of
  `store/schema.rs`. The parent renumbers migrations during the rebase.
- **Builds:** several tasks build at once on one machine. Run cargo with
  `nice -n 19` and `CARGO_BUILD_JOBS=6`. While working, test only your
  crate (`-p`). Run the full workspace checks once, at the end.
- **Shared files:** besides your own modules, keep edits to
  `core/commands.rs`, `core/mod.rs`, `core/state.rs`,
  `core/identity.rs`, `handler.rs` and `config.rs` as small as you can,
  and list them in your report.

## Wave 1 (in parallel)

### A. Server: messages and retention (`core/messages.rs`, `store/messages.rs`, `store/sqlite/messages.rs`)

- **MSG with `edit` and `react` (5.3):** move `msg` out of
  `core/commands.rs` into `core/messages.rs`.
  - The target must be a message in the same conversation, not
    deleted, and not itself an edit or reaction (`not-found`).
  - Only the author of the target may edit it.
  - Reactions are at most 64 bytes. The same reaction from the same
    uid to the same message gets `OK` with the existing seq, unless that
    reaction was deleted.
  - cids still come first (7.6).
- **DELETE (5.4):**
  - The author, or in rooms a moderator, owner or operator, may delete.
  - Authors may delete their own messages even in rooms they can no
    longer read: check authorship before the reading rules. Otherwise,
    rooms you cannot see get `not-found`.
  - Only MSG events can be deleted (ENC waits for M5a). An already
    deleted target gets `not-found`.
  - Erase the target's text (`event_text`), and with a message, its
    edits and reactions. Its replies stay. Mark them `deleted`. Report
    copies are separate and are not touched.
  - The DELETE event is recorded and broadcast like any event.
- **HISTORY and RELATED (7.2, 7.3):** placeholders with the `deleted`
  tag, no text and no file tags. RELATED with `after`, `limit` and
  `more`, and the reading rules of HISTORY.
- **Retention (7.5):**
  - A background task that expires events by the shorter of the server's
    period and the room's, in seq order, stopping at the first event
    that is not old enough. Seqs are never reused (the `head` column
    already ensures it).
  - Shortening either period applies to stored events at the next run.
    Expose a way to run it now, so ADMIN SET and SET can trigger it and
    tests can call it with a fake clock.
  - Expired cids and read markers need no change.
- **ADMIN PURGE (10.4):** operators only. Deletes `<uid>`'s messages in
  every conversation as DELETE does, with the operator as the DELETE
  event's `from`, optionally only the last `hours`. Replies
  `OK deleted=<count>`. Guest uids cover every message sent under the
  name.
- **UNREGISTER `purge=yes` (4.8):** replace the `not-supported` branch
  in `core/identity.rs` with a purge of the identity's messages, using
  the same code.
- **Tests:** in `core/` with the existing `Harness`, including the
  edge cases above.

### B. Server: rooms and moderation (`core/moderation.rs`, `store/moderation.rs`, `store/sqlite/moderation.rs`)

- **SET (6.2):** `topic` for mods and owners; `public`, `guests` and
  `retention` for owners. `e2ee` gets `forbidden`. `history` gets
  `forbidden` (no room is encrypted yet). Unknown keys get
  `not-supported`. Trailing spaces in keyword and number values are
  ignored; topics keep them.
  - `retention` is at least 1 and not longer than the server's period
    (`forbidden`). Trigger task A's retention run if it exists, or leave
    a `TODO(M4 rebase)` comment if it does not yet.
  - `guests read` stops guests in the room from sending messages,
    reactions and typing. `guests none` removes them with a PART each.
- **ROLE and ROLES (6.3):** the target is a member, or holds `owner` or
  `mod`. Setting a departed role-holder to `member` takes the role. The
  only owner cannot change their own role (`last-owner`). ROLES needs
  read permission and lists owners and mods, members or not.
- **INVITE (6.4):** for mods, owners and operators. Guests cannot be
  invited. Inviting a member records nothing and gets a plain `OK`. The
  INVITE event also goes to the invitee's connections, as a
  notification that does not make them a member.
- **KICK and BAN (6.4):**
  - Moderators act only on plain members. Owners and operators act on
    anyone.
  - KICK of a non-member gets `not-found`, even if they hold a role.
  - BAN works on non-members too. It deletes the target's invitation.
  - Both take away the target's role. The event reaches the target's
    connections before they stop receiving the room.
  - BAN of a guest bans the uid only.
- **UNBAN and BANS (6.4).**
- **Permissions:** operators have owner rights in every room (Section
  10). Reuse and extend the helpers in `core/commands.rs`.
- **Tests:** in `core/`, including every row of the table in 6.3.

### C. Server: reports, `ADMIN ROOMS` and `ADMIN DROP` (`core/reports.rs`, `store/reports.rs`, `store/sqlite/reports.rs`)

- **REPORT (5.8)** of MSG events in rooms. Direct conversations and
  REPORTENC reply `not-supported` until M5a.
  - Anyone who can read the message may report it, guests included.
    Not your own (`forbidden`), not deleted (`not-found`), reason up to
    512 bytes.
  - The same uid reporting the same message gets the existing id.
  - Rate-limit reports per uid (reuse `core/rate.rs`), with
    `rate-limited` and `retry`.
  - Keep a copy of the event as it was. The copy outlives DELETE,
    retention and ADMIN DROP. `reports.conv` cascades on delete today:
    add a migration so reports keep the room's name and id themselves
    and survive a drop.
  - Send the two lines, both tagged `report`, to every reviewer's
    connections: the room's owners and mods (whether or not they are
    members) and the operators. Only operators get `from` on the REPORT
    line.
- **REPORTS `<room>`**, **RESOLVE** (with `RESOLVED <id>` to the other
  reviewers) and **ADMIN REPORTS**.
- **ADMIN ROOMS (10.4):** every room, private ones too, paged like LIST.
- **ADMIN DROP (10.4):**
  - Members are removed as if kicked. `@id=<id> DROP <room> [reason]`
    goes to every connection in the room.
  - Roles, invitations, bans, events and settings are deleted. Open
    reports stay.
  - Use the existing `dropped` flag, so commands waiting on the room's
    lock get `not-found`.
  - A room named in `config.rooms` is created again at once, empty,
    with a new id.
- **Tests:** in `core/`.

### D. Server: the rest of ADMIN (`core/admin.rs`, `store/admin.rs`, `store/sqlite/admin.rs`)

Every ADMIN command gets `forbidden` for non-operators.

- **OPS, OP and DEOP (10.1):** stored, and applied to the hub's
  operator set at once. Guests cannot be operators. Configured operators
  cannot be removed (`forbidden`).
- **BAN, UNBAN and BANS (10.2):**
  - Identity bans and domain bans (`*@example.net`, with subdomains).
    AUTH and REGISTER get `forbidden`. A banned identity's open
    connections are closed with BYE.
  - A connected guest's uid bans its IPv4 address, or its IPv6 `/64`,
    and closes its connection. BANS lists it under the address.
  - Address and prefix bans stop GUEST from those addresses.
- **WHO, DISCONNECT and NOTICE (10.3).**
- **KEYS, ADDKEY, DELKEY and UNREGISTER (10.5)**, reusing the KEY and
  UNREGISTER code. DELKEY may remove the last key. Not-hosted
  identities get `not-found`.
- **SET (10.6):** `guests`, `registration`, `retention` and `welcome`,
  stored and shown in INFO at once.
  - `guests no` ends connected guests' sessions with BYE, and their
    PARTs, as in 4.2.
  - `retention` triggers task A's retention run, as in B.
- **Tests:** in `core/`.

### E. librisala and `risala-cli` (`crates/librisala`, `crates/risala-cli`)

- **Messages:** DELETE through the outbox like the other sends. Applying
  DELETE events: erase text, drop the target's edits and reactions, and
  make an edit's previous version current again. RELATED placeholders
  remove stored edits and reactions. Check what already exists first.
- **Rooms:** settings (SET and snapshot SET lines), roles (ROLE events,
  ROLES), INVITE, KICK, BAN, UNBAN and BANS as APIs.
  - An INVITE for your own account that is not a member is a
    notification, not history. If you thought you were a member, SYNC.
  - A KICK or BAN of yourself ends membership, and is not stored as the
    room's history.
  - DROP: ignore one whose id is not the stored one; otherwise remove
    the room and its history.
- **Reports:** REPORT, REPORTS and RESOLVE. Report lines (with the
  `report` tag) and RESOLVED are delivered to the app as reports, never
  stored as events.
- **ADMIN:** every command, with typed results (operators, bans,
  connections, rooms, keys, settings). NOTICE reaches the app.
- **CLI:** subcommands for all of the above.
- **Tests** with the scripted server. Wave 2 adds tests against
  `TestServer`.

## Announcement-only rooms (after the review fixes land)

Added at the user's request (PLAN.md section 5, item 38): the room
setting `send all|mods`. Built once the two review-fix tasks are
rebased, so nothing clashes in `risala-server`.

- **risala-proto:** `RoomSetting::Send` with `all` and `mods`.
- **Server:** stored with the other room settings (a migration), sent
  in snapshot SET lines, owners only. Under `mods`, MSG from plain
  members and guests gets `forbidden` unless it is a reaction, and so
  does their TYPING. SET of `send` in an encrypted room gets
  `encrypted` (no room is encrypted before M5a).
- **librisala and CLI:** the setting in `RoomInfo` and the cached
  conversation (`ConversationInfo::announcements`), and `set_setting`
  for it. The client does not refuse a message itself, since it cannot
  always know whether the account is an operator (offline, before it
  signs in): the server refuses it, and the outbox entry fails as
  `Rejected`.
- **Tests:** unit and end-to-end. Add `S: SET #general send all` to the
  overview example in 1.4 and to README.md's copy of it, which the
  example tests replay.
- **M5a:** the `send` field of the conversation extension, and devices
  dropping members' non-reactions (12.11).
