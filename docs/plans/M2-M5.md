# M2 and M5: the server for guests and rooms, and librisala's core

This is the working plan for milestones M2 and M5 in
[PLAN.md](../../PLAN.md). [SPEC.md](../../SPEC.md) is the source of truth.
If this file and the spec disagree, the spec wins. Report the
disagreement instead of working around it.

## Goal

At the end of this work:

- **M2.** Two `openssl s_client` sessions chat as guests: GUEST, JOIN,
  PART, LIST, MSG, HISTORY, SYNC, INFO, PING and QUIT, with everything
  stored in SQLite. `risalad` runs from a TOML file, or from no file at
  all, as a development server with a generated self-signed certificate.
- **M5 (core).** librisala connects with trust on first use, signs in,
  syncs into its SQLite cache, works offline from that cache, and
  recovers from dropped connections without losing or duplicating
  messages. `risala-cli` shows all of this from a terminal.

M5 also needs AUTH, which arrives with M3. Until then, librisala's
sign-in as an identity is tested against a scripted server, and the
end-to-end tests use guests.

## How the work is split

Each task runs in its own git worktree, branched from the scaffold
commit, and commits there. The parent merges the branches.

- **Own your files.** Edit only the files and directories your task
  lists. Do not edit `lib.rs`, `handler.rs`, `config.rs`, `addr.rs`,
  `Cargo.toml` or another task's module. If you need a change there,
  make the smallest one you can, and list it in your report so the
  parent can reconcile it.
- **Done means:** `cargo fmt --all --check`,
  `cargo clippy --workspace --all-targets -- -D warnings` and
  `cargo test --workspace` all pass, inside `nix develop` (the plain
  shell has no `cargo fmt`). Every public item has a doc comment, naming
  the spec section it implements where there is one. Tests do not
  depend on the network, on fixed ports (bind port 0) or on timing
  luck. Tests that need the `openssl` binary skip themselves when it is
  not on PATH.
- **Commits:** plain messages in the imperative, prefixed with the
  crate, for example "server: store events in SQLite". No Co-Authored-By
  lines and no mention of AI tools.
- **Report:** what you built, the public API in a few lines, what you
  left out, and anything in the spec that was unclear.

## Conventions

- Use the typed values from `risala-proto` (`Request`, `Command`,
  `ServerMessage`, `ServerLine`, `Event`, `Room`, `Uid`, `Seq`, `Id`,
  `Timestamp` and so on). Do not parse or format lines by hand.
- Text stays escaped, as on the wire (3.4). Nothing in the server ever
  unescapes it except to check that MSG text is not blank, which
  `risala-proto` already does.
- Times come from `Timestamp::now()`, behind a clock you can replace in
  tests where timing matters.
- Random values (nonces, ids, cids, keys) come from `getrandom`.
- Log with `tracing`. Never log message text, signatures or keys.
- SQLite: WAL mode, `foreign_keys=ON`, a busy timeout, short
  transactions, and a schema version in `PRAGMA user_version` with
  migrations from the start. Blocking SQLite calls stay off the async
  runtime's worker threads (`spawn_blocking` or a dedicated thread).

## Wave 1 (in parallel)

### A. Server core (`crates/risala-server/src/core/`, `src/store/`)

The hub: it implements `handler::Handler`. It owns all state, all
checks and all fan-out. It is tested by driving the `Handler` trait
directly with `handler::conn_channel` queues, with no sockets or TLS.

**Store** (`src/store/`): a `Store` trait and a SQLite implementation.
Design the schema for the whole protocol, not only M2, so that M3 and M4
add tables rather than redo them. It needs at least:

- conversations: an id that is never reused (5.1), a kind (room or
  direct), a name, a head seq and a creation time
- events: conversation, seq, time, author, verb, tags and parameters,
  with a `deleted` flag and the text kept separately so DELETE can erase
  it (5.4)
- room settings, room membership (identities persist; guests do not),
  roles, invitations and room bans, empty for now
- server settings (10.6), first filled from `config.server`
- cids, scoped to a conversation id (7.6)

Appending an event assigns the next seq and stores the event in one
transaction. The hub sends an event only after it is stored, so seqs
never have gaps (5.2, PLAN.md 3.2). Ids are 12 random characters of
`a-z 0-9`.

**Hub** (`src/core/`): `Hub::new(config: Config, store: impl Store)` and
`Hub::open(config: Config)`, which opens SQLite at
`config.database_path()`. Rooms in `config.rooms` are created at startup
if missing, with no owner and no events.

Behaviour for M2:

- **Greeting (4.1).** On `open`, send `RISALA 1 <host> <nonce>
  [<welcome>]`: `<host>` is the SNI name, or `config.hostname`; the nonce
  is 32 random bytes; the welcome text comes from the server settings.
  Close with BYE if the connection has not signed in within
  `limits.sign_in_secs`.
- **Before sign-in,** only INFO (without a room), GUEST, AUTH, REGISTER,
  PING, PONG and QUIT are accepted; anything else gets
  `ERR not-authenticated` (`Command::allowed_before_sign_in`).
  Signing in twice gets `ERR already-authenticated`.
- **GUEST (4.2):** `ERR forbidden` if guests are off, `ERR name-taken`
  if a connected guest has the name, otherwise `OK uid=~<name>`.
- **JOIN, PART (6.1).** JOIN: the JOIN event with the `id` tag, then
  snapshot SET lines for `topic`, `public`, `guests` and `retention` in
  that order, then `OK id=<id> head=<seq>`. A member gets the settings
  and the OK, with no event. A room that does not exist is
  `ERR not-found`, since guests cannot create rooms. Guests need
  `guests` to be `read` or `write`, and cannot join private rooms, since
  they cannot be invited. PART when not a member is `ERR not-found`. A
  guest's connection closing records a PART with no reason in each of
  its rooms (4.2).
- **MSG (5.3).** Rooms only, for now. You must be a member, and a guest
  needs `guests write` (otherwise `ERR forbidden`). Support `reply`
  (with its target checks) and `cid` (7.6: for guests, within one
  connection). For now, `edit`, `react` and `file` get
  `ERR not-supported`. The sender receives the event before `OK seq=`.
- **HISTORY (7.2)** with `after`, `before` and `limit` exactly as
  specified, capped at `limits.max_page`, ending with `OK id= more=`.
  This includes reading public rooms you are not in, and the guest
  rules.
- **SYNC (7.1):** one CONV line per conversation the connection is in,
  then OK. `read` is 0 for guests.
- **LIST (6.1):** public rooms only, in byte order, with `after`,
  `limit` (default 100, capped at `limits.max_list`) and `OK more=`.
- **INFO (8.5, 6.2).** INFO returns `OK version=1 guests=<yes|no>
  register=no retention=<..> push=no upload=no`. `INFO <room>` returns
  the snapshot SETs, then `OK id= members= head= role= joined=`. A guest
  that has joined has the role `member`. A room the asker may not see is
  `ERR not-found`.
  - **Spec gap:** a room created from the configuration has no events
    until someone joins, so there is no seq to report as `head`. For
    now, leave `head` out in that case, and note it in the code. The
    spec needs a decision.
- **PING** gets OK. **PONG** gets nothing. **QUIT** gets OK, then
  `Close { bye: None }`.
- **Commands from later milestones** that parse get `ERR not-supported`.
- **Fan-out.** An event goes to every connection of every member,
  including the author's. Within a conversation, every connection gets
  events in seq order, even when two connections post at the same time.
  So assign the seq, store and enqueue under one per-room lock.
  `ConnHandle::send` never blocks; a full queue kills only that
  connection.
- **Errors.** Store failures give `ERR internal` and are logged.

Tests: one test per behaviour above, written as transcripts against
`Handler` (send `Request`s, assert on the `ServerMessage`s in each
queue). Include ordering with two posters, the guest auto-PART, HISTORY
paging at every edge, and a restart that reopens the same SQLite file
and keeps rooms, ids and history.

### B. Server network layer (`crates/risala-server/src/net/`)

Everything between the socket and the `Handler`. It is tested with a
stub `Handler`, so it does not need A.

- **API.** `net::Server::bind(config: &Config, handler: Arc<H>) ->
  io::Result<Server>` binds every address in `config.listen`, so tests
  can use port 0, then `server.local_addrs()` and
  `server.run(shutdown: impl Future<Output = ()>)`.
- **TLS (2.1).** TLS 1.3 only, with the ring provider. It offers the
  ALPN `risala/1` and accepts clients that offer none.
  - Certificates are chosen by SNI: the first entry in
    `config.tls.certs` whose certificate is valid for the name (use
    `webpki::EndEntityCert`), or else the first entry.
  - Certificates reload without dropping connections (2.2): poll the
    files' modification times every 60 seconds, and also reload on
    SIGHUP. A reload that fails keeps the old certificate and logs an
    error.
  - When `config.tls.certs` is empty, generate a self-signed certificate
    (rcgen) for `config.hostname`, store it under
    `<state_dir>/selfsigned/`, reuse it on later starts, and log its
    fingerprint (`risala_proto::fingerprint`). It must match what
    Appendix A's openssl pipeline prints.
  - The handshake times out after 10 seconds.
- **Connection task.**
  - Read through `frame::LineDecoder` with `MAX_CLIENT_LINE`. Ignore
    empty lines except that they reset timers (2.3, 11).
  - A line that is too long gets `ERR too-long`. A line that does not
    parse gets the code from `ParseError::code()` (bad-syntax,
    unknown-command, too-long), carrying the line's `ref` when one can
    be read (3.6; see `LineDecoder::next_line_with_ref` and
    `Request::ref_of`).
  - Every reply goes through the connection's own `ConnHandle`, so it
    stays in order with the core's responses.
  - Commands go to `Handler::command` one at a time, each awaited before
    the next is read.
  - The write half drains the `ConnReceiver`, writing each line with
    LF. On `Close` it writes BYE if there is one, sends TLS
    `close_notify` and closes. When `killed()` fires, it drops the
    connection.
  - `Handler::closed` is called exactly once, however the connection
    ends.
- **Keepalive (11).** After `limits.idle_ping_secs` with nothing
  received, send `PING <token>`. After `limits.ping_timeout_secs` more,
  send `BYE ping timeout` and close. Any line received resets both
  timers.
- **Shutdown.** When `shutdown` resolves, stop accepting, send `BYE
  server shutting down` to every connection, wait up to 5 seconds for
  the queues to drain, then return.
- **Limits.** Cap concurrent connections at a constant for now, and note
  that per-address limits come in M9.

Tests use a tokio-rustls client with a verifier that accepts the test
certificate. They cover:

- the greeting from a stub handler, with SNI and without
- ALPN offered and not offered
- too-long lines, bad UTF-8, control characters and CRLF
- `ref` on parse errors
- empty lines resetting the idle timer
- PING, then BYE after the timeout (with short limits)
- a slow reader being killed
- certificate selection by SNI and a reload after replacing the files
- shutdown
- the generated certificate's fingerprint matching an openssl pipeline
  (skipped without openssl)

### C. librisala connections (`crates/librisala/src/conn/`)

- **TLS client (2.1, 2.2).**
  - TLS 1.3 only, ring, ALPN `risala/1`. SNI is the host of the
    `ServerAddr`. An IP address sends no SNI.
  - A custom `ServerCertVerifier` implements 2.2 exactly, using a
    `TrustStore`:
    1. A CA-valid certificate is accepted and recorded as `Ca`,
       replacing any pin.
    2. Otherwise, compute the fingerprint of the leaf's
       SubjectPublicKeyInfo. With no record, fail with an error that
       carries the fingerprint, so the app can ask the user, store
       `Pinned` and connect again.
    3. A matching pin is accepted.
    4. A different pin, or a `Ca` record, fails with an error carrying
       both values.
  - Handshake signatures are still verified in every case.
  - The CA check uses `rustls-platform-verifier` by default. It is
    replaceable, so tests can supply their own root.
- **Session.**
  - `Session::connect(addr, trust, options)` reads the greeting and
    rejects any version other than 1 (3.8).
  - `guest(name)`, `auth(identity, &SecretKey)` and
    `register(name, &SecretKey)` sign in. Sign with the host the client
    sent in SNI, not the one in the greeting (4.5).
  - `request(Command) -> Result<Response>`, where `Response` holds the
    `ref`-tagged lines and the final `OK` or `ERR`.
    - Give every request a fresh `ref` and match the final response to
      its request in order (3.6).
    - An `OK` or `ERR` that cannot be parsed still ends its command, as
      a general failure (2.3).
  - Every other line goes, in arrival order, to an
    `mpsc::Receiver<ServerMessage>` of incoming lines. That includes
    live events, PRESENCE, NOTICE, READ, TYPING, DROP and BYE.
  - A server PING is answered with PONG straight away, inside the
    session (11).
  - While idle, the session PINGs the server and treats a missing answer
    as a dead connection.
- **Reconnects.** A supervisor reconnects with exponential backoff and
  jitter, signs in again through a callback, and reports state changes
  (connecting, connected, signed in, waiting to retry, failed for good,
  for example after a trust error or `auth-failed`).
- **Keys (`conn/keys.rs`).** A `KeyStore` trait for platform key
  storage (PLAN.md 3.3), with `MemoryKeyStore` and a `FileKeyStore` that
  keeps PKCS#8 PEM files with mode 0600, for the CLI and for Linux
  until libsecret. Also:
  - `generate_device_key()` from getrandom
  - the key file line for a device (4.4)
  - AUTH and REGISTER signing helpers on top of `risala_proto::auth`

Tests run an in-test TLS server (tokio-rustls, rcgen) that plays
scripted transcripts. They cover:

- every trust case in 2.2, including CA to pin and pin to CA, with a
  test root CA standing in for the platform
- the fingerprint matching Appendix A's openssl pipeline (skipped
  without openssl)
- a wrong protocol version
- guest and auth sign-in, the auth signature checked against the
  Appendix B vectors
- responses matched with interleaved live events
- an unparseable `OK`
- PING answered with PONG
- reconnects after the server drops the connection

### D. librisala store and sync engine (`crates/librisala/src/store/`, `src/sync/`)

**Store.** A SQLite cache, safe to open from two processes at once (the
iOS notification extension, PLAN.md 3.3). Tables:

- servers, and trust records (implement `addr::TrustStore` on it)
- accounts (server and uid)
- conversations, per account. Each has:
  - the conversation name
  - the id it was last known by
  - the sync point (7.1)
  - the last head reported
  - the read marker
- events, keyed by conversation and seq, with the full line as received
  plus the indexed columns the UI needs: time, author, verb, relation,
  deleted, file metadata
- derived tables for each message's current text after edits, reaction
  counts per message and reaction, and room membership and settings,
  updated in the same transaction as the events that change them
- the outbox

Discarding a conversation's history, when its id changes (7.1) or after
DROP, is one transaction. Expose reads the UI needs: a page of messages
with their current text and reactions, unread counts, and a full export
of a conversation for offline use.

**Sync engine.** A state machine with no I/O, one per signed-in
connection. It implements 7.1 to 7.3 and 7.6 exactly. Read
`proofs/sync/RisalaSync.tla` and `proofs/README.md`: the model found
real gaps, and the engine must keep its invariants.

- **Sync points.** Keep a sync point per conversation, not "the newest
  seq stored". Catching up runs `HISTORY after=<sync point>` while
  `more=1`. The sync point advances over each page and over any stored
  events that directly follow it.
- **Ids.** Compare the id from SYNC, JOIN (the `id` tag), INFO,
  HISTORY's `OK id=` and RELATED's `OK id=` with the stored one, and
  start the conversation afresh when they differ. Do the same when a
  reported head is below the newest stored seq.
- **Live events.** Store no live event for a conversation until its id
  is known on this connection. Drop duplicates by seq. A live event
  moves the sync point only if it directly follows it.
- **Notifications.** INVITE events that reach a non-member, and KICK or
  BAN events that reach their target, are notifications, not history
  (6.4). A conversation missing from SYNC means the account has left it.
  DROP removes the room.
- **Older pages.** Load them lazily with `HISTORY before=`, then
  `RELATED` for their edits and reactions (7.3).
- **Outbox (7.6).**
  - Each queued MSG gets a cid of at least 16 random characters, and is
    bound to the conversation's id when queued.
  - After a reconnect, resend what has no `OK` yet, but only while the
    id still matches. If the room was recreated, mark the message failed
    instead of sending it into the new room.
  - Match `OK seq=` to the stored event.
- **Interface.** The engine takes server lines and command results as
  input. It returns the commands to send next, and the changes for the
  UI: inserted, updated and removed messages, and the conversation list.
  It writes through the store. A wave 2 task connects it to C's session.

Tests:

- unit tests for each rule above
- property tests: a simulated server that drops connections at random
  points, recreates rooms, expires events and delivers live events
  concurrently with pages. After any run, the store holds exactly the
  server's events for each conversation, in order, with no gaps or
  duplicates, and the outbox sent each message at most once per id.
- the scenarios TLC found in `proofs/sync`

## Wave 2 (after wave 1 is merged)

### E. Server wiring and end-to-end tests

- `risala_server::run(config, shutdown)` connects A and B. `risalad`
  reads `--config <path>` (default: none, giving a development server)
  and logs through `tracing-subscriber` with `RUST_LOG`.
- `risala_server::testing` (behind a `testing` feature, or public and
  documented as such): a `TestServer` on a temporary directory and port
  0, and a line-level `TestClient` over TLS. librisala's and
  risala-cli's tests use them too.
- Transcript tests over TLS for every M2 behaviour. Every spec example
  M2 covers becomes a test. Add an `openssl s_client` smoke test,
  skipped without openssl.
- Add a "Running a server" section to README.md. Make
  `nix flake check` pass.

### F. librisala client API and risala-cli

- `Client` (many servers and accounts), `Account` and `Conversation`.
  - A `Timeline` sends the UI diffs, driving C's session and D's
    engine.
  - Send through the outbox.
  - Offline reads come from the store.
- `risala-cli`, using clap, with these commands:
  - `connect` and `trust`: show the fingerprint and accept it
  - `guest`
  - `join`, `part`, `list`
  - `send`, `log`: read from the cache, offline
  - `sync`, and `export` for offline download
  - `chat`: a simple interactive line mode
  - `keygen` and `keyline`, for M3
- Integration tests against an in-process `risalad`:
  - the connection drops at random points during sync and during sends
  - nothing is lost or duplicated
  - offline reads work after the server is stopped

## Wave 3: review

A reviewer reads the server and librisala against the spec and lists
problems: disagreements with the spec, ambiguities, missing cases,
races, and API problems for M3 and the apps. The parent fixes them,
then reruns the full checks and `nix flake check`.
